# Feature Specification: git.rs — Rust Reimplementation of Git

**Feature Branch**: `002-git-rs-product-spec`

**Created**: 2026-09-20

**Status**: Draft

**Input**: User description: "Define the overall product specification for this repository. Project: git.rs — a full Rust reimplementation of Git. Create a clean-room Rust implementation of Git that aims to reproduce Git's observable behavior, command-line interface, repository format, object model, references, index, configuration, transport, merge behavior, and other essential Git functionality as faithfully as practical. The existing Git implementation is written primarily in C. Treat upstream Git behavior, documentation, tests, and repository formats as the behavioral reference. Do NOT simply translate C code line-by-line. Requirements: Rust-native architecture and idiomatic Rust; preserve compatibility with existing Git repositories; existing repositories readable by git.rs whenever the corresponding feature is implemented; git.rs capable of creating repositories standard Git can understand; CLI behavior should closely match Git including commands, options, exit codes, stdout/stderr and relevant environment variables; preserve on-disk compatibility; no unnecessary breaking deviations; prefer incremental implementation with explicit compatibility boundaries; project must remain buildable and testable throughout."

---

## Overview and Evidence Base

This specification defines the product-level contract for **git.rs**, a standalone,
pure-Rust reimplementation of Git. It is derived from the repository as it exists
today, not from aspiration:

- **Reference and oracle**: the upstream C git tree at `v2.55.0-540` in the repository
  root (C sources, `builtin/`, `t/`, `Documentation/`). The C tree is *never* linked
  into the Rust build; it is read as a specification and executed as a test oracle.
- **Active work**: the Rust workspace under `crates/` (`git-hash`, `git-varint`,
  `git-pretty`, `git-date`, `git-config`, `git-core`, `git-cli`, `git-command`,
  `git-object`, `git-commitgraph`, `git-odb`, `git-revision`, `git-diff`,
  `git-index`, `git-refs`, `git-merge`, `git-attributes`, `xtask`).
- **Locked strategy**: standalone rewrite (gitoxide-style), no FFI, core-object
  layer first, phased roadmap (`docs/plan/README.md`).
- **Committed regression baseline**: `crates/scoreboard.json`, regenerated by
  `cargo xtask scoreboard`, which fails on regression.

**Relationship to existing spec `001-c-to-rust-conversion`.** Spec 001 frames the
project as "all files all units converted one by one" from C to Rust. The locked
plan explicitly rejects line-by-line translation as the strategy ("Treat upstream
Git behavior… as the behavioral reference. Do NOT simply translate C code line by
line"). This specification asserts the **behavioral** framing and treats 001's
file-by-file framing as superseded. See Open Questions Q1.

---

## Project Vision

Provide a Git implementation that is **indistinguishable from Git in observable
behavior and entirely different in construction**: a memory-safe, idiomatic Rust
codebase that interoperates byte-for-byte with the existing Git ecosystem.

A user should be able to point git.rs at any repository created by standard Git,
use it, and hand the result back to standard Git — with neither side able to tell
which tool touched it, and no FFI, shim, or C code in the Rust binary.

---

## Scope

### In Scope

1. **The CLI surface**: commands, options, exit codes, stdout, stderr, and
   environment variables, matching C git as the reference.
2. **The repository format**: objects (loose and packed), refs, `HEAD`, index,
   config, pack/idx/rev-index, multi-pack-index, commit-graph, reftable — readable
   and writable byte-compatibly where implemented.
3. **The object model and revision model**: blobs, trees, commits, tags, annotated
   tags, replacement objects, grafts, revision walking and ordering.
4. **History and merge semantics**: diff, merge, conflict representation, merge
   bases, reachability, rerere-class conflict state.
5. **Index and worktree behavior**: stat cache, racy-clean handling, checkout/
   reset/read-tree semantics, ignore and attribute rules.
6. **Transport and network operations**, per the plan's Phase E.

### Compatibility Boundaries Are Explicit

Every implemented capability MUST declare its boundary: what it reads, what it
writes, and which standard-Git version's behavior it is validated against
(currently v2.55.0-540). Capabilities not yet implemented MUST fail loudly and
predictably rather than partially succeed.

---

## Non-Goals

1. **No FFI and no C linkage.** The Rust binary never calls into C git; the C
   binary is never linked into the Rust build. This is not negotiable and is not a
   temporary state.
2. **Not a line-by-line translation.** C source structure, module boundaries, and
   internal APIs are not the porting target; observable behavior is.
3. **No new user-facing features.** git.rs does not invent options, formats, or
   behaviors that Git lacks.
4. **No silent deviation.** Every known divergence is a logged, reviewed backlog
   entry, not an undocumented difference.
5. **Legacy and third-party bridge tools out of scope**: `cvs*`, `svn`, `p4`,
   `quiltimport`, `archimport`, GUI/tooling wrappers (`gitweb`, `git-gui`,
   `instaweb`, `difftool`/`mergetool` front-ends).
6. **Not a library-first product.** The deliverable is a working `git`
   replacement binary; the crates are internal structure, not a promised public
   API with stability guarantees.
7. **Bit-identical reimplementation of human-facing prose is not a hard
   requirement** — see the MUST/SHOULD split under Compatibility Goals.

## Compatibility Goals

The specification distinguishes three obligation levels.

### MUST — non-negotiable, machine-verified

These are gating. A change that breaks any of these does not land.

1. **Exit codes MUST match** C git exactly, including `129` for usage errors and
   `1` for "unknown command".
2. **Machine-readable output MUST be byte-identical** to C git: plumbing output,
   `--porcelain`/`-z`/`--format` output, object IDs, index and pack file bytes,
   ref file contents, config file contents, and any output a script would parse.
3. **On-disk formats MUST be byte-compatible in both directions** for every
   format the implementation claims to support:
   - Standard Git MUST be able to read and validate artifacts git.rs writes
     (`git fsck`, `git verify-pack`, `git commit-graph verify`,
     `git multi-pack-index verify`).
   - git.rs MUST be able to read artifacts standard Git produced.
4. **No FFI and no C linkage** in the shipped Rust binary.
5. **`t/` scripts MUST be the oracle.** Where C source and the `t/` suite
   disagree, `t/` wins.
6. **No regression against the committed `scoreboard.json` baseline.**
7. **The workspace MUST remain buildable and testable** at every commit.

### SHOULD — expected, with documented exceptions allowed

1. **stderr diagnostics SHOULD match** C git, including `usage:` blocks and
   `fatal:`/`error:`/`warning:` prefixes and wording.
2. **Human-facing prose SHOULD match** (log formatting, diff headers, status
   text, advice messages).
3. **Documented intentional deviations SHOULD be logged** in the project's
   follow-up backlog, with the reason and the affected `t/` scripts named.
4. **Performance SHOULD be within the same order of magnitude** as C git on
   comparable operations.
5. **Environment-variable handling SHOULD match**, including `GIT_DIR`,
   `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`,
   `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CONFIG_*`, `GIT_AUTHOR_*`/
   `GIT_COMMITTER_*`, `GIT_CEILING_DIRECTORIES`, `GIT_NAMESPACE`, and the
   `GIT_TRACE*` family.
6. **Configuration semantics SHOULD match**, including scope precedence
   (system → global → local → worktree), includes, and `includeIf` conditions.

### Intentionally Rust-Specific — no compatibility obligation

These are deliberate internal differences with no observable effect:

1. **Architecture.** Crate boundaries, module layout, and internal APIs are
   Rust-native and need not mirror C files (`strbuf.c` need not map 1:1 to a
   module, though the ported `StringBuf` primitive deliberately reproduces C
   `strbuf` semantics where those semantics are observable).
2. **Memory model.** Ownership, borrow checking, and lifetimes replace manual
   allocation and refcounting. No observable effect is permitted.
3. **Concurrency.** Rust's thread model may replace C's; parallel operation MUST
   NOT change output bytes or ordering guarantees.
4. **Error handling.** `Result`-based internal error propagation replaces
   `die()`/`error()` longjmp-style control flow. The *externally visible* exit
   code, message, and stream MUST still match.
5. **Dependencies.** Pure-Rust crates may be used where C used bundled code, as
   long as byte-level output is unaffected.
6. **Version string.** The ported version is pinned to the C version being
   ported, and MUST be kept in sync when rebasing onto new upstream.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Interoperate with an Existing Repository (Priority: P1)

A developer has a repository created and maintained by standard Git. They run a
git.rs command against it and get the same answer standard Git would give, then
hand the repository back to standard Git with no repair step.

**Why this priority**: Reading existing repositories is the entry condition for
the entire project. Without it, nothing else has value — the ecosystem's
repositories are the data.

**Independent Test**: For each implemented command, run it with both binaries on
the same repository fixture and compare stdout, stderr, and exit code byte for
byte; then run standard Git's integrity checks (`fsck`, `verify-pack`,
`commit-graph verify`, `multi-pack-index verify`) over the repository.

**Acceptance Scenarios**:

1. **Given** a repository populated by standard Git (loose objects, packs, a
   multi-pack-index, a commit-graph, packed refs), **When** git.rs reads objects,
   walks history, and resolves refs, **Then** its output is byte-identical to
   standard Git's and the repository is unmodified.
2. **Given** a repository written by git.rs, **When** standard Git runs `fsck`
   and the relevant `verify` subcommands, **Then** all report success with no
   warnings or errors.
3. **Given** a repository containing packed refs, a worktree, and a non-default
   object directory, **When** git.rs resolves `HEAD` and refs, **Then** results
   match standard Git including symref indirection and worktree-specific refs.

---

### User Story 2 - Replace Git in a Script and Get Identical Results (Priority: P1)

A CI pipeline or script invokes a git command and parses the output. Swapping in
git.rs changes nothing: same bytes, same exit code, same error text.

**Why this priority**: Scripts are how Git is actually consumed, and they are the
strictest compatibility test. A pipeline that silently changes meaning is worse
than one that fails.

**Independent Test**: Run an identical invocation under both binaries across the
command surface, comparing stdout, stderr, and exit status byte for byte —
including failure paths (bad revision, dirty index, missing repository, wrong
argument count).

**Acceptance Scenarios**:

1. **Given** the same arguments and repository state, **When** both binaries run,
   **Then** stdout, stderr, and exit code are byte-identical.
2. **Given** a usage error (missing argument, unknown option, unknown
   subcommand), **When** both binaries run, **Then** the exit code matches
   (`129` for usage, `1` for unknown command) and the message matches.
3. **Given** a plumbing command with a machine-readable format flag
   (`--format`, `-z`, `--porcelain`, `--batch`), **When** both binaries run,
   **Then** the output is byte-identical even where human-prose parity is only a
   SHOULD.

---

### User Story 3 - Create Repositories and Artifacts Standard Git Accepts (Priority: P2)

A developer initializes a repository, commits, and packs objects with git.rs.
Standard Git clones, fetches, and verifies the result without noticing.

**Why this priority**: Write-path compatibility is what makes git.rs a real
implementation rather than a read-only inspector; it is P2 only because reading
is a prerequisite.

**Independent Test**: Produce artifacts (loose objects, packs, indexes, refs,
commit-graph, multi-pack-index) with git.rs and validate them with standard Git's
verification commands; then run the `t/` scripts for those areas through the
dispatcher.

**Acceptance Scenarios**:

1. **Given** a fresh directory, **When** git.rs initializes and populates a
   repository, **Then** standard Git reads it, verifies it, and performs
   operations on it without repair.
2. **Given** objects packed by git.rs, **When** standard Git runs
   `verify-pack`, **Then** it reports no errors.
3. **Given** an index written by git.rs, **When** standard Git runs
   `status`/`diff`, **Then** it reports the same worktree state git.rs reports.

---

### User Story 4 - Follow C Git's Behavior Where the Format Is Deferred (Priority: P2)

A user's operation depends on a subsystem git.rs has not fully implemented (for
example delta compression on write, or a specific revision-ordering mode). The
result is still correct — either completed by an alternate conforming path or
refused with a clear, matching error — never silently wrong.

**Why this priority**: Incremental delivery is a stated requirement; the
credibility of the whole project depends on the unimplemented parts being
*traceable*, not invisible.

**Independent Test**: For every deferred capability, confirm either a conforming
fallback that passes crosswise verification, or a matching failure mode; every
such case is named in the follow-up backlog with its affecting test scripts.

**Acceptance Scenarios**:

1. **Given** a capability documented as deferred, **When** a user triggers it,
   **Then** the behavior is either byte-identical to C git or fails with a
   recorded, reviewed divergence.
2. **Given** a pack written by git.rs without delta compression, **When**
   standard Git verifies and reads it, **Then** it remains valid and
   byte-compatible even though C git would have produced smaller output.
3. **Given** a deferred feature is implemented, **When** it lands, **Then** the
   backlog entry is removed, a crosswise test is added, and the scoreboard
   baseline is intentionally updated.

---

### User Story 5 - Extend the Implementation Without Breaking Compatibility (Priority: P3)

A contributor adds a command or deepens an existing one. The gates tell them
immediately whether compatibility held, and their change cannot silently regress
another area.

**Why this priority**: The project's viability depends on change being *safe*.
This is P3 only because it serves the other four stories rather than end users.

**Independent Test**: Make a change; run the workspace tests, property tests,
crosswise suites, and scoreboard check; confirm all gates are green and coverage
on touched crates meets the threshold.

**Acceptance Scenarios**:

1. **Given** a new command port, **When** it is added, **Then** it is dispatched
   by the CLI, routed by the dispatcher, covered by a registered crosswise suite,
   and present in the scoreboard.
2. **Given** a behavioral change, **When** the scoreboard check runs, **Then** it
   fails unless the baseline is intentionally regenerated in the same change.
3. **Given** any commit, **When** the workspace is built and tested, **Then** it
   builds and its tests pass.

### Edge Cases

- **Empty repository** (`git init` with no commits): `HEAD` points at an unborn
  branch; commands MUST report the same "no commits yet"/unknown-revision
  behavior and exit codes as C git.
- **Corrupt objects and packs**: truncated zlib streams, mismatched lengths, bad
  CRC/SHA, malformed deltas. git.rs MUST fail with C git's message and exit code,
  never panic, and never write.
- **Object-ID collision and abbreviation ambiguity**: abbreviated IDs MUST resolve
  to the same object as C git or report the same ambiguity error; collision-
  detecting hashing behavior must match the reference.
- **Repository discovery edge cases**: inside `.git`, above a worktree root, under
  `GIT_CEILING_DIRECTORIES`, via `GIT_DIR` without a worktree, in a bare
  repository, in a linked worktree, with a `--separate-git-dir` gitfile, and
  through symlinks.
- **Symlink and filesystem limits**: symlinked worktrees and gitdir paths; very
  long paths.
- **Concurrent modification**: another process mutating refs, the index, or packs
  mid-operation. git.rs MUST behave like C git (lock files, retries, refusals),
  and MUST NOT corrupt state.
- **Interrupted writes**: killed mid-`commit`/mid-repack. No partially written
  object or index may be left where standard Git would consider it valid.
- **Clock skew and time zones**: commit dates out of order, future timestamps,
  non-local offsets, DST boundaries, leap years.
- **Locale and encoding**: non-ASCII paths, filenames with newlines/quotes,
  decomposed Unicode, invalid UTF-8 in paths and commit messages; output quoting
  and escaping MUST match C git's rules.
- **Case-insensitive and case-preserving filesystems** (macOS/Windows): rename and
  status behavior.
- **Large repositories**: deep history, very large blobs, many packs — no
  integer overflow, no unbounded memory growth, no quadratic blowup.
- **Zero-state CLI**: `git` with no arguments, unknown subcommand, `--version`,
  `--help`, and stale/misconfigured `PATH` — exit codes and stream choice match.
- **Stale lock files and permission errors**: read-only repositories, read-only
  `.git`, unwritable object store.

## Requirements *(mandatory)*

### Functional Requirements

#### Object model and storage

- **FR-001**: System MUST read loose objects (blob, tree, commit, tag) with
  standard Git's zlib framing and header format, and MUST reject malformed
  objects with matching diagnostics.
- **FR-002**: System MUST write loose objects that standard Git accepts,
  including correct permissions and atomic replacement via temporary files.
- **FR-003**: System MUST read packfiles and their indexes, including delta
  chains (offset and reference deltas), and MUST verify pack checksums.
- **FR-004**: System MUST write packfiles and indexes that standard Git verifies
  via `verify-pack` and reads without repair, even where an internal encoding
  choice (for example, delta compression) is deferred.
- **FR-005**: System MUST support the multi-pack-index, pack rev-index,
  commit-graph, and replace-object formats to the extent claimed by the
  implementation, reading artifacts produced by standard Git.
- **FR-006**: System MUST honor alternate object directories and the object
  directory environment overrides with C git's precedence.
- **FR-007**: System MUST NOT panic, hang, or write on any malformed input;
  arbitrary bytes reaching a parser produce a matching error or a matching
  success.

#### Revision and history

- **FR-008**: System MUST resolve revision specifications to the same commits as
  C git, including abbreviated IDs, ref names, `HEAD`-relative forms
  (`HEAD~n`, `HEAD^n`, `@{n}`, `@{upstream}`), ranges (`A..B`, `A...B`,
  `^A`), and the same ambiguity and "unknown revision" errors.
- **FR-009**: System MUST walk history with the same set of commits, the same
  ordering under each ordering mode (default, topological, date,
  author-date, first-parent), and the same `--objects` expansion as C git.
- **FR-010**: System MUST implement commit-graph-accelerated traversal that
  produces identical results to unaccelerated traversal.
- **FR-011**: System MUST respect grafts and replace objects where C git does, and
  produce identical output when they are present.
- **FR-012**: System MUST reproduce C git's date generation, parsing, and
  formatting, including the local-timezone offset stored in idents and
  date-format options.

#### Refs, index, and worktree

- **FR-013**: System MUST read and write loose refs, packed refs, symbolic refs,
  and `HEAD` with C git's resolution, precedence, and error behavior.
- **FR-014**: System MUST implement ref updates with C git's locking and atomicity
  guarantees, including compare-and-swap semantics and `--stdin` transaction
  batches.
- **FR-015**: System MUST read and write every index version C git supports for
  the claimed boundary (v2 through v4 + split/sparse), preserving extension
  chunks (cache-tree, resolve-undo, untracked-cache, fsmonitor) with correct
  invalidation.
- **FR-016**: System MUST detect worktree state (modified, staged, deleted,
  untracked, ignored) by the same rules as C git, including racy-clean handling
  and stat-cache shortcuts, and MUST produce identical `status` output in every
  supported format.
- **FR-017**: System MUST apply ignore rules (`.gitignore`, `.git/info/exclude`,
  `core.excludesFile`, precedence, negation, directory rules) and attribute rules
  (`.gitattributes`, macro/info/system sources) identically to C git.

#### Diff, merge, and history transformation

- **FR-018**: System MUST produce diffs with C git's exact output format:
  headers, hunk ranges, context lines, "\ No newline at end of file", binary
  handling, and function-context hunk headers.
- **FR-019**: System MUST implement rename and copy detection with results
  matching C git's for the same options and thresholds.
- **FR-020**: System MUST reproduce merge results — content, conflict markers,
  index stages, and messages — identically to C git for the supported merge
  strategies, including merge bases and recursive bases.
- **FR-021**: System MUST provide `--exit-code` and `--quiet` semantics identical
  to C git for diff-family commands.

#### CLI and configuration

- **FR-022**: System MUST implement each ported command's argument parsing with
  C git's accepted abbreviations, `--` separator behavior, option/operand
  interleaving, and rejection of malformed options.
- **FR-023**: System MUST return C git's exit codes, including `129` for usage
  errors and `1` for unknown commands.
- **FR-024**: System MUST write errors and diagnostics to stderr and results to
  stdout, matching C git's stream choice in every case, and MUST NOT interleave
  them incorrectly when both streams are redirected.
- **FR-025**: System MUST implement repository discovery and worktree detection
  per C git, honoring `GIT_DIR`, `GIT_WORK_TREE`, `GIT_CEILING_DIRECTORIES`,
  gitfiles, bare repositories, and linked worktrees.
- **FR-026**: System MUST implement configuration reading with C git's scope
  precedence, includes and conditional includes, and value-type interpretation,
  and configuration writing that produces byte-compatible files.
- **FR-027**: System MUST support C git's environment-variable surface for every
  implemented capability, including identity, object-directory, index-file,
  tracing, and locale variables.
- **FR-028**: System MUST emit `--version` output consistent with the pinned
  upstream version, and MUST keep that pin synchronized when the reference C tree
  moves.
- **FR-029**: System MUST implement global options (`-C`, `-c`, `--git-dir`,
  `--work-tree`, `--bare`, `--no-pager`, `--paginate`, `--literal-pathspecs`)
  with C git's placement rules and interactions.

#### Transport

- **FR-030**: System MUST implement the pkt-line framing and protocol state
  machine compatibly with standard Git, for each transport it claims to support.
- **FR-031**: System MUST interoperate with a standard Git peer for the
  implemented transport paths — fetching from and pushing to a standard Git
  server or local repository — producing identical resulting repositories and
  identical user-visible output.
- **FR-032**: System MUST perform negotiation (ref advertisement, wants/haves,
  shallow/deepen, filters) so that the objects transferred match what C git would
  transfer for the same request.

#### Deferred-capability discipline

- **FR-033**: Any capability not implemented MUST fail with a matching, non-
  misleading result — never a partial success that leaves state C git would
  consider inconsistent.
- **FR-034**: Every intentional divergence MUST be recorded in the project's
  follow-up backlog with its reason, scope, and the test scripts that exercise
  it.

### Key Entities

- **Repository**: A directory tree with an object store, refs, configuration, and
  optionally a worktree and index. May be bare, have a separate git dir, or be a
  linked worktree. Has a hash algorithm (SHA-1 or SHA-256, and possibly with a
  compatible-object mapping between them).
- **Object**: An immutable, content-addressed unit: blob, tree, commit, or tag.
  Identified by the hash of its typed, length-prefixed content.
- **Object store**: The union of loose objects, packfiles, alternates, and
  derived caches (multi-pack-index, rev-index, commit-graph, bitmaps) that makes
  objects findable.
- **Reference**: A named pointer to an object, loose or packed, direct or
  symbolic; plus its reflog of prior values. Namespaced, with `HEAD` as the
  worktree's current-ref symref.
- **Index**: The staged-state cache between worktree and next commit, carrying
  per-entry stat data, stage numbers for conflicts, path entries with compression
  and prefix modes, and extension chunks.
- **Worktree**: A checked-out tree plus its `.git` linkage, tracked state, ignore
  and attribute rules.
- **Configuration**: Layered key/value settings (system, global, local, worktree,
  command-line) with includes and typed values.
- **Revision specification**: A user-supplied expression (name, ID, range,
  relative form) that resolves to a set of commits or objects.
- **Patch / diff**: A structured description of change between two tree states,
  with the change-detection options that produced it.
- **Merge**: A combined result of two or more histories, with base selection,
  conflict representation, and index/working-tree effects.
- **Transport / remote**: An endpoint and protocol session through which objects
  and refs move between repositories.
- **Test fixture / oracle result**: A recorded standard-Git behavior (output,
  exit code, artifact bytes) against which git.rs is compared.

## Non-Functional Requirements

- **NFR-001 (Safety)**: The Rust crates contain no `unsafe` in the default build
  unless individually justified and reviewed; any `unsafe` block carries a
  documented soundness argument.
- **NFR-002 (Robustness)**: No input — malformed objects, packs, indexes,
  configuration, patches, or protocol traffic — may cause a panic, an abort, an
  infinite loop, or unbounded memory growth. Fuzz targets for the parsers run
  clean for a fixed budget.
- **NFR-003 (No corruption)**: No failure mode may leave a repository in a state
  standard Git considers corrupt. Writes are atomic (temporary file + rename) and
  lock-protected in the same places C git locks.
- **NFR-004 (Buildability)**: `cargo build --workspace` and
  `cargo test --workspace` succeed at every commit on a supported toolchain
  (pinned minimum Rust version), from a clean checkout, without the C tree built.
- **NFR-005 (Determinism)**: Identical inputs produce identical bytes across runs
  and across platforms where C git is likewise deterministic. No timestamps,
  iteration order from hash maps, or environment leakage may alter output bytes.
- **NFR-006 (Coverage)**: Line coverage on each phase's crates meets the
  project's threshold, measured by the workspace's coverage tooling.
- **NFR-007 (Performance)**: Operations complete within the same order of
  magnitude as C git on the same repository. Specifically excluded from strict
  parity: operations whose internal encoding is deliberately deferred, provided
  output bytes and validity are unaffected.
- **NFR-008 (Portability)**: Correct behavior on Linux, macOS, and Windows to the
  same extent C git supports them, including platform-specific path, case-
  sensitivity, symlink, and permission semantics.
- **NFR-009 (Observability)**: The tracing environment variables produce output
  that lets a developer compare behavior against C git without a debugger.
- **NFR-010 (Dependency discipline)**: Third-party dependencies are pure Rust,
  license-compatible with the project's GPL-2.0-only licensing, and may not alter
  observable output bytes.
- **NFR-011 (Maintainability)**: Each capability is independently testable; a
  contributor can change one subsystem and learn from the gates alone whether
  compatibility held.

## CLI Compatibility Requirements

This section is the product contract for the command-line surface.

1. **Command surface.** Commands are recognized by the same names and aliases as
   C git. Every subcommand implemented is dispatched internally; commands not yet
   implemented MUST be routed to a real git or refused with a matching error, and
   the routing set MUST be tracked explicitly so "implemented" is never
   ambiguous.
2. **Argument grammar.** Option parsing matches C git: long-option abbreviation,
   `--opt=value` and `--opt value`, short-option clustering, `--` terminator,
   options after operands where C git allows it, and the same rejection of
   ambiguous or unknown options.
3. **Streams.** Results on stdout; diagnostics, progress, and advice on stderr.
   Progress and pager behavior match C git's triggering conditions (TTY
   detection, `--no-pager`, config). Output MUST NOT differ when stdout is not a
   TTY except where C git itself differs.
4. **Exit codes.** `0` success; `1` for "unknown command" and for ordinary
   failures C git reports as 1; `129` for usage errors; command-specific codes
   (`--exit-code`, `--quiet`, diff status, `check-ignore`, `merge-base`) match
   exactly.
5. **Usage and help.** Invalid usage prints the same `usage:` block to stderr and
   exits `129`. `--help` and `help <cmd>` behavior match, including man-page
   lookup failures.
6. **Global options.** `-C`, `-c`, `--exec-path`, `--git-dir`, `--work-tree`,
   `--bare`, `--namespace`, `--paginate`/`--no-pager`, `--literal-pathspecs`,
   `--no-replace-objects`, `--version` behave and position exactly as in C git.
7. **Environment.** The Git environment-variable contract is honored (FR-027),
   including `GIT_*` identity, discovery, object store, index, config, tracing,
   and locale variables.
8. **Identity.** `user.name`/`user.email` resolution order (config scopes, then
   environment, then auto-detection), `author`/`committer` split, and the
   resulting ident line format (including timezone offset) match.
9. **Pinning.** The reported version tracks the pinned upstream version and is
   updated in the same change as the reference tree moves.
10. **Shim discipline.** When a new command is ported, it is added to the
    dispatcher, wired into the CLI dispatch, and given a crosswise suite in the
    same change. A command is not "ported" until all three hold.

## Repository-Format Compatibility Requirements

This section is the product contract for on-disk state.

1. **Objects.** Loose object framing (type, length header, zlib), content
   addressing, and file placement/permissions match standard Git. Objects written
   by git.rs are readable and verifiable by standard Git, and vice versa.
2. **Packs.** Pack header, object encoding, delta chains, trailer checksum, and
   `.idx` v2 layout (including the large-offset table) match. Packs written by
   git.rs pass `verify-pack`; packs written by standard Git are read correctly,
   including thin packs after base resolution.
3. **Refs.** Loose ref files, `packed-refs` (including peeled tag lines and
   sorted ordering), symrefs, `HEAD`, per-worktree refs, and namespaces match.
   Ref updates use the same lock-file and atomic-rename discipline, and the same
   recovery behavior after a stale lock.
4. **Reflog.** Reflog files under the logs area have the same path derivation,
   line format, and append semantics, including identity and timestamp fields.
5. **Index.** Index files have the same header, entry encoding, path compression
   (v4), extension chunk order and contents, and signature footer, with the same
   checksum coverage. Standard Git reads git.rs indexes without refresh-induced
   diffs; git.rs reads standard Git's without loss.
6. **Configuration.** Config files match format and serialization: sections,
   subsection quoting, key normalization, value escaping and continuation, and
   include semantics. Round-tripping a written file through standard Git
   preserves meaning and bytes.
7. **Derived caches.** Multi-pack-index (including its chunks), pack rev-index,
   commit-graph, and any bitmap support are read and written with the same layout,
   and standard Git's `verify` subcommands accept them.
8. **Alternates and shared stores.** The alternates file format and resolution
   order match, including relative-path semantics.
9. **Attributes and ignores.** Rule files use the same pattern grammar, including
   `**`, negation, directory-only rules, and macro definitions.
10. **Metadata files.** `FETCH_HEAD`, `MERGE_HEAD`, `ORIG_HEAD`, `CHERRY_PICK_HEAD`,
    `REBASE_HEAD`, `AUTO_MERGE`, sequencer state, `COMMIT_EDITMSG`, `SQUASH_MSG`,
    and worktree/gitfile linkage have the same names, locations, and formats.
11. **Hash algorithm.** The supported hash algorithms match. Where two algorithms
    can coexist in one repository, the object-format mapping behaves as C git
    specifies.
12. **Additivity.** A git.rs write MUST NOT introduce a file, extension, or byte
    sequence that standard Git's integrity checks flag as unknown-and-invalid.
    Unknown-but-tolerated extensions must be exactly those C git tolerates.

## Testing Strategy

Testing is the mechanism by which the compatibility contract is enforced; it is
not a separate quality activity.

### Layers

1. **The `t/` suite is the oracle.** The upstream shell test suite runs against
   git.rs through the dispatcher. A ported command is validated by passing the
   same scripts the C implementation passes. Where C source and the suite
   disagree, the suite wins.
2. **Crosswise differential testing.** For each subsystem and phase, the same
   invocation runs under git.rs and standard Git on identical inputs; stdout,
   stderr, and exit code must be byte-identical. Every suite is registered so it
   runs under one command.
3. **Crosswise on-disk compatibility.** Both directions: standard Git verifies
   what git.rs writes; git.rs reads what standard Git wrote. Verification uses
   standard Git's own `fsck`/`verify` tooling, not self-reported success.
4. **Unit and property tests.** Parsers and serializers are covered by property
   tests asserting no panics on arbitrary input and round-trip invariants (for
   example, write-then-read equality, and re-serialization stability).
5. **Golden fixtures.** Generated once from the oracle and committed, so format
   regressions are caught without needing the C tree built.
6. **Regression scoreboard.** The committed `t/` results baseline is regenerated
   by tooling and fails the build on regression; it is updated only as a
   deliberate act accompanying an intended behavior change.
7. **Fuzzing.** Parser entry points for objects, packs, indexes, caches, config,
   refs, and patch text are fuzzed for a fixed budget.
8. **Coverage.** Coverage thresholds are measured per phase's crates.
9. **Failure-path testing.** Every edge case in the Edge Cases section is
   exercised in both binaries and compared, including the error text and exit
   code — not only happy paths.
10. **Interoperability scenarios.** Realistic multi-step workflows (init →
    add → commit → pack → verify; clone-shape fetch; worktree operations) run
    with the two implementations interleaved, so mixed-tool history is proven.

### Gate

A change lands only when the workspace builds and tests pass, the differential
suites are byte-identical, crosswise compatibility holds, the scoreboard shows no
regression, and coverage on touched crates meets the threshold. These gates are
enforced by tooling, not by convention.

## Migration and Implementation Strategy

1. **Behavioral porting, not translation.** Read the C to understand behavior;
   write Rust that produces the same observable results. Structural similarity to
   C is not a goal and is not evidence of correctness.
2. **Incremental with explicit boundaries.** The plan proceeds in phases by
   subsystem dependency: foundation → loose objects → packs and indexes → derived
   caches → object/revision model → diff → index and worktree → refs → merge →
   object conversion and integrity. Each phase states what it reads, what it
   writes, and what remains deferred.
3. **Depth before breadth.** A routed command reaches full option parity before a
   new command begins. A shallow routing that accepts a flag but ignores it is a
   compatibility hazard, not progress.
4. **Every step closes with its gates.** No phase is "done" until its tests,
   crosswise suites, scoreboard, coverage, and named test scripts pass.
5. **Deviations are logged, not hidden.** Intentional divergences are recorded
   with reason and blast radius, and are removed when the capability lands.
6. **The shim is the migration boundary.** Until a command is ported, the
   dispatcher routes it to a real git; this keeps the full suite runnable
   throughout development and keeps the boundary honest and inspectable.
7. **Reference pinning.** The C tree version is fixed for a conversion cycle and
   updating it is a deliberate, tested change.
8. **Always buildable, always testable.** The workspace builds and tests from a
   clean checkout at every commit, independent of the C tree's build state.

## Phased Feature Boundaries

Phases are defined by subsystem dependency and each names its compatibility
boundary. Status reflects the repository's current plan documents.

### Phase A — Foundation and deepening of routed commands

**Boundary**: local object store, refs, index, diff, dates, and the ignore/
attribute rule engines; prerequisite for all porcelain.

Content: collision-detecting hashing; repository discovery and `--git-dir`/
`--work-tree` threading through all commands; batch object reading with format
specifiers; shared abbreviation resolution (short IDs, refs, `HEAD~n`);
`rev-parse` completion; revision-walk and log option surface; a pretty-printing
engine; diff engine completion (cached, context counts, stat family, rename/copy
detection, diff filters, pickaxe, binary); hunk-header function context;
`count-objects -v`; the `.gitignore`/`.gitattributes` engine; local-timezone date
and ident handling; delta compression on the pack write path.

**Done when**: routed commands reach option parity for their documented surface,
each item's crosswise suite is byte-identical, and the named scripts pass.

### Phase B — Workflow core ("a usable repository")

**Boundary**: creating and advancing a repository's history without network.

Content: `git init`; index extensions and v3/v4 support; `git add`; write-tree
and read-tree (one/two/three-way); `git commit`; full `status`; unpack-trees plus
checkout/switch/restore/reset; `rm`, `mv`, `clean`; `show`, `shortlog`,
`describe`, `name-rev`, `whatchanged`; `apply` completion.

**Done when**: a user can create a repository, stage, commit, inspect, and move
around history with behavior identical to C git for the covered surface.

### Phase C — History and merge completeness

**Boundary**: multi-parent history mutation and ref history.

Content: merge via the ort-class engine (rename detection, directory/file
conflicts, recursive bases, index merge); merge-tree, extended merge-base,
cherry; cherry-pick and revert (sequencer subset); rebase; reflog read/write and
reflog-aware updates; packed-refs writing, ref locking and transactions, symref
writes, worktree-specific refs; the small independent command set (pack-refs,
mktag, check-ref-format, stripspace, var, patch-id, check-ignore, check-attr,
interpret-trailers, show-index, unpack-file, diff-files, diff-index, and others);
full `config` command; notes/replace/worktree/bisect/stash/range-diff/rerere/
blame/grep/archive; `fsck` completion.

**Done when**: merge and history-editing behavior matches C git on the merge and
sequencer suites, and reflog/ref-transaction semantics hold.

### Phase D — On-disk format completeness

**Boundary**: the derived-cache and packing surface, in both directions.

Content: pack bitmaps and reachability acceleration; cruft packs and pack mtimes;
commit-graph writing with chains and bloom queries; multi-pack-index optional
chunks, incremental MIDX, and preferred-pack; `index-pack`; `repack`, `gc`,
`prune`, `prune-packed`, `maintenance`, `pack-redundant`, `replay`; SHA-1↔SHA-256
object conversion.

**Done when**: every format git.rs writes verifies under standard Git, and every
format standard Git writes is read correctly.

### Phase E — Network and transport

**Boundary**: everything crossing a repository boundary.

Content: pkt-line and protocol state machine; local/file transport and
`ls-remote`; fetch with negotiation; push with refspec and force rules; the `git://`
daemon transport; smart HTTP; SSH; clone and pull; remote and credential handling;
bundle and bundle-uri; fast-export/fast-import.

**Done when**: git.rs interoperates with a standard Git peer, producing identical
repositories and identical user-visible output, for the claimed transports.

### Phase F — Stretch and low priority

Signature verification, patch-series tooling (`am`, `format-patch`, mailinfo),
mail/IMAP senders, tool front-ends, sparse and split index rollout, smudge/clean
filters and line-ending conversion, and remaining ancillary commands. Explicitly
out of scope: legacy VCS bridges and GUI tooling (see Non-Goals).

## Compatibility and Correctness Criteria

A capability is correct when all of the following hold; these map directly to the
obligation levels in Compatibility Goals.

1. **Behavioral identity**: on the same inputs, stdout, stderr, and exit code are
   byte-identical to the reference (MUST for machine-readable output and exit
   codes; SHOULD for human prose).
2. **Format identity**: artifacts are readable and verifiable by standard Git in
   both directions (MUST).
3. **Suite identity**: the corresponding upstream test scripts pass through the
   dispatcher (MUST).
4. **No regression**: the committed scoreboard baseline does not regress (MUST).
5. **Robustness**: malformed input never panics, hangs, or writes (MUST).
6. **Atomicity**: interrupted operations leave no state standard Git considers
   valid-but-wrong (MUST).
7. **Determinism**: repeated identical runs produce identical bytes (MUST).
8. **Declared boundary**: every deferred capability is either conforming via an
   alternate path or fails with a recorded divergence (MUST).
9. **Performance envelope**: within the same order of magnitude as the reference
   (SHOULD).
10. **Coverage**: touched crates meet the project's coverage threshold in the
    same change (MUST).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For every command in the shipped dispatcher set, an identical
  invocation under git.rs and standard Git on the same fixture produces identical
  stdout, stderr, and exit code — 100% of registered differential cases, with
  zero unexplained differences.
- **SC-002**: 100% of artifacts git.rs writes are accepted by standard Git's own
  integrity verification commands with no errors and no repair step.
- **SC-003**: 100% of the in-scope upstream test scripts in the committed baseline
  pass through git.rs, with the baseline showing zero regressions across
  consecutive runs.
- **SC-004**: The workspace builds and its full test suite passes from a clean
  checkout at every commit, with no dependency on a built C tree.
- **SC-005**: No panic, hang, or unintended write is observed in any fuzz or
  malformed-input campaign run to a fixed budget.
- **SC-006**: Coverage on each phase's crates reaches the project threshold (90%
  line coverage) at phase completion.
- **SC-007**: A user can complete an end-to-end workflow — create a repository,
  stage, commit, inspect history, diff, branch, merge, and pack — using only
  git.rs, then perform further operations on that repository with standard Git,
  with neither tool reporting an inconsistency.
- **SC-008**: Every intentional divergence from C git is recorded with its reason
  and exercising tests; no divergence is discovered by a user rather than
  documented by the project.
- **SC-009**: For comparable operations on a large repository, git.rs completes
  within one order of magnitude of the reference implementation's wall-clock time.
- **SC-010**: A new command or deepened capability can be contributed by a
  developer unfamiliar with the area, with the automated gates alone determining
  whether compatibility held — measured by the gates being sufficient to catch a
  deliberately introduced behavioral deviation.

## Assumptions

- **Behavioral reference is the `t/` suite over the C source.** When they
  disagree, the suite is authoritative.
- **The reference version is pinned** to `v2.55.0-540` for the current conversion
  cycle; moving it is a deliberate, separately tested change. Repository
  documents that cite a slightly different describe/commit suffix reflect
  intermediate tree state and do not change the pin.
- **Compatibility means byte-identity on machine-readable surfaces.** Human prose
  parity is a strong preference, not a gate; the working assumption is that
  fidelity here is the safest path to the gate-level requirements.
- **SHA-1 is the default hash algorithm** for fixtures and crosswise testing
  unless a test specifically targets SHA-256; the repository's current documented
  deviation on collision detection is a backlog item, not a design choice.
- **The `t/` suite can run against git.rs through a dispatcher**, with unported
  commands routed to standard Git; this keeps the suite green during incremental
  development and is how "no regression" is measured.
- **The committed scoreboard is a true baseline**, updated only as a deliberate
  act accompanying intended behavior change, never to make a failure disappear.
- **Standard Git's own verification commands are trusted** as the arbiter of
  on-disk validity; git.rs does not self-certify format correctness.
- **The C tree's working-tree build artifacts are not part of git.rs.** Committed
  object files and wrapper scripts in the C tree are not evidence about the Rust
  implementation's state.
- **Platform defaults follow C git**, including platform-specific behavior for
  case sensitivity, symlinks, and file permissions.
- **Dependencies are pure Rust and license-compatible**, and never change
  observable output bytes.
- **Performance parity is explicitly bounded** to the same order of magnitude,
  because internal encoding choices (for example, deferred delta compression) may
  trade size for simplicity without affecting correctness or compatibility.

## Risks and Open Questions

### Risks

1. **Scope is effectively unbounded.** A full Git reimplementation spans
   decades of accumulated behavior and edge cases. Without a hard, published
   boundary, "remaining work" never reaches zero and the project's success
   criterion is never testable. *Mitigation*: explicit phased boundaries and a
   declared dispatcher set as the definition of shipped surface.
2. **`t/` suite infrastructure dependency.** Running the real suite requires
   components (test-tool equivalents, helper binaries) that may not exist in
   Rust yet, or may require the C build — which weakens the "no C dependency"
   claim for the oracle path. *Mitigation*: track the test-infrastructure track
   explicitly; distinguish "suite passes" from "suite passes without a C build."
3. **Differential-test blind spots.** Byte-identical output on the fixtures we
   choose does not prove parity on inputs we never construct. *Mitigation*:
   property/fuzz testing plus the upstream suite as an independent oracle.
4. **Shallow routing masquerading as progress.** Accepting an option without
   implementing its semantics is more dangerous than rejecting it, because it
   converts a loud failure into a silent wrong answer. *Mitigation*: depth-before-
   breadth and per-command option-parity gates.
5. **Deferred-encoding divergence.** Deliberate simplifications (for example,
   non-deltified packs, or a non-collision-detecting hash) can propagate into
   repository size, performance, or security properties even though format
   validity holds. *Mitigation*: keep these as named backlog items with explicit
   re-evaluation triggers.
6. **Platform semantics drift.** Filesystem case sensitivity, path length, and
   symlink behavior differ across supported platforms and can produce
   incompatibilities that only appear for some users. *Mitigation*: cross-platform
   scenarios in the differential and interoperability suites.
7. **Concurrency and crash safety.** Locking and atomicity bugs are rare, hard to
   reproduce, and corrupt user data. *Mitigation*: explicit interruption and
   concurrent-mutation scenarios in the edge cases; invariant tests on repository
   validity after failures.
8. **Baseline pressure.** The committed scoreboard creates pressure to make
   failures disappear by updating the baseline. *Mitigation*: regenerate only with
   an intentional behavior change in the same commit.
9. **Documentation and decision drift.** Repository documents already conflict
   (for example, spec 001's framing versus the locked plan; network listed as out
   of scope in one document and as a full phase in another). *Mitigation*:
   resolve the open questions below and keep a single authoritative statement of
   scope.
10. **Zero `unsafe` versus performance and platform access.** Some low-level
    operations may appear to require unsafe code. *Mitigation*: per-case
    justification, documented soundness, and isolation behind safe interfaces.

### Open Questions

- **Q1 — Relationship to spec 001.** Spec `001-c-to-rust-conversion` describes the
  project as converting every C file and unit one by one, which contradicts the
  repository's locked strategy (behavioral, non-line-by-line, standalone rewrite).
  Should this specification **supersede** 001, **complement** it as a higher-level
  product contract, or should 001 be revised to match the locked plan? *Why it
  matters*: two authoritative framings of "what this project is" will keep
  producing contradictory plans and status reports.

- **Q2 — Shipped product boundary.** The plan's overview document states that
  network/transport, porcelain, submodules, and the like are explicitly out of
  the core-object-layer scope, while a later plan document adds a full network
  phase and a definition of done requiring every in-scope command to be ported.
  Which is the product boundary for this specification — **local core only**,
  **local core plus porcelain and history editing**, or **full Git including
  network**? *Why it matters*: it determines whether SC-003/SC-007 are
  achievable, and whether "done" is defined at all.

- **Q3 — Performance obligation.** Is "same order of magnitude as C git" the
  correct bar, or is there a stronger expectation (for example, no consistent
  regression beyond a specific factor on a named benchmark repository)?
  *Why it matters*: deferred internal encodings may be acceptable under the
  looser bar and unacceptable under a stricter one, which changes the priority of
  the packing work.

- **Q4 — `t/` oracle completeness.** Is the long-term intent that the full
  upstream suite runs against git.rs with **no** standard Git process involved
  (a stricter, stronger claim), or is routing unported commands to standard Git
  permanently acceptable? *Why it matters*: it sets the real target for the test
  infrastructure track and changes the meaning of "baseline 100%."

- **Q5 — Unsupported-command failure mode.** For commands not yet ported, should
  git.rs **delegate** to a standard Git binary when present, or **fail with a
  clear message**? Delegation maximizes usability during development but can mask
  incompleteness; failing makes the boundary honest but reduces usefulness.
  *Why it matters*: it affects user trust and the meaning of the test baseline.

- **Q6 — Constitution status.** The project constitution file is still the
  unfilled template. Should governance principles (gate definitions, deviation
  policy, no-FFI rule) be ratified into it, making them binding on planning?
  *Why it matters*: the compatibility rules currently live in prose documentation
  and task documents rather than in a governing artifact.

## Glossary of Obligation Levels

| Marker | Meaning | Enforcement |
|---|---|---|
| **MUST** | Required for compatibility; a violation is a defect | Automated gate: build, crosswise, scoreboard, coverage, fuzz |
| **SHOULD** | Strongly expected; deviations allowed if recorded with reason | Review + documented backlog entry |
| **Rust-specific** | Deliberate internal difference with no observable effect | Must not change output, exit codes, or on-disk bytes |
