# Test Automation Infrastructure

"Fully automated tests for every part" means every gate in this document is a
single command, runs in CI on every commit, and regressions fail the build.
This document defines the machinery. Each phase file lists the specific tests
that use it.

## 1. Test taxonomy

| Type | Tool | Runs on | Verifies |
|---|---|---|---|
| Unit | `cargo test` | every commit | function-level behavior, error paths |
| Doc-test | `cargo test` | every commit | API contract from rustdoc examples |
| Property | `proptest` | every commit | parsers/serializers round-trip, invariants, no panic on arbitrary input |
| Differential | integration tests shelling to C `git` | every commit | byte-identical CLI/format behavior vs C git |
| Crosswise format | integration tests | every commit | C↔Rust on-disk compatibility + C `fsck`/`verify` |
| Golden | committed fixtures | every commit | stable known-good outputs |
| Fuzz | `cargo-fuzz` | CI short run | corruption resilience (t5303/t5313-style) |
| t/ scoreboard | `cargo xtask scoreboard` | every commit | pass% of the C test suite via shim dispatch |
| Coverage gate | `cargo llvm-cov` | every commit | ≥ 90% line coverage on core crates |

## 2. Workspace layout

```
crates/*/tests/             integration tests (differential + crosswise format tests)
crates/git-test/            Rust reimplementation of t/helper/test-tool subcommands
tests/fixtures/             golden repos + objects, committed, regenerated by script
tests/differential/         harness shelling out to the C git binary
xtask/                      cargo xtask automation
scripts/shim-git            dispatcher git wrapper for t/ scoreboard
.github/workflows/          CI (unit / differential / scoreboard / fuzz)
```

## 3. Differential harness

`tests/differential/` is a small crate whose tests shell out to a C `git`
binary. The C git is built from this repository (`make` or `meson`) by CI /
`cargo xtask differential`. A typical test:

1. Creates a fixture repo (checked-in, or built with C git at test time).
2. Runs C `git <cmd>` and the Rust CLI on identical inputs.
3. Asserts byte-identical stdout/stderr/exit codes.

Conventions:
- The C binary path is resolved from `GIT_REFERENCE` env var
  (`tests/differential` fixtures default to a sibling `reference-git` build).
- Fixture repos live under `tests/fixtures/` and are produced by
  `cargo xtask gen-fixtures` using a **pinned C git version**; committed
  fixtures are verified unchanged by CI (checksum file `tests/fixtures/.checksums`).
- Differential tests are marked `#[ignore]`-by-default and enabled via the
  `differential` cargo feature so the normal unit suite has no C dependency.

## 4. Crosswise on-disk compatibility

These tests verify both directions for every on-disk format:

- **C → Rust**: repository/objects/files produced by C git are read by Rust and
  produce identical logical results.
- **Rust → C**: repository/objects/files produced by Rust are validated by C
  git (`git fsck`, `git verify-pack`, `git commit-graph verify`,
  `git multi-pack-index verify`, `git cat-file`, `git status`, …).

The strongest end-to-end crosswise test is `t/t1016-compatObjectFormat.sh`
(sha1↔sha256 interoperability), which becomes a Rust-driven scoreboard test in
Phase 9.

## 5. t/ scoreboard

The entire `t/` suite is the compatibility oracle. A shim `git` script
(`scripts/shim-git`) dispatches: ported commands → the Rust binary, unported
commands → the C git binary. `cargo xtask scoreboard` then runs the suite and
writes `scoreboard.json` (per-test-script pass/fail + counts).

Policy:
- `scoreboard.json` is committed; CI fails if the current run regresses
  against the baseline (strict decrease in passing scripts for covered
  commands).
- A phase's milestone = its listed `t/` scripts pass at 100%.
- The scoreboard also reports the "Rust coverage" percentage (which `t/`
  scripts exercise only Rust code), used as a progress metric.

Constraint: the `t/` suite calls the `test-tool` helper binary. The Rust port
must therefore provide `crates/git-test` (a Rust `test-tool` replacement) for
the subset of subcommands used by core-object-layer tests.

## 6. Fuzz

- `cargo-fuzz` targets per parser: pack, idx, midx, commit-graph, bitmap,
  index, config, reftable, loose-object header, xdiff.
- Corpora seeded from `t/` corruption fixtures (`t/t5302`, `t/t5303`,
  `t/t5313`) and from `tests/fixtures/`.
- CI runs each target for a fixed short budget (e.g. 10 min) on every commit;
  nightly runs use a larger budget.

## 7. Coverage gate

- `cargo llvm-cov --workspace --fail-under-lines 90` runs in CI for core crates
  (git-hash, git-object, git-odb, git-commitgraph, git-index, git-refs,
  git-revision, git-diff, git-merge, git-fsck, git-core, git-config,
  git-date, git-varint).
- Test code is excluded; `#[cfg(test)]`/test-support helpers are filtered.

## 8. `cargo xtask` commands

| Command | Action |
|---|---|
| `cargo xtask test` | unit + doc + proptest, no C dependency |
| `cargo xtask differential` | build C reference git, run differential + crosswise suites |
| `cargo xtask scoreboard` | build shim + Rust CLI, run `t/`, update/verify `scoreboard.json` |
| `cargo xtask fuzz` | run fuzz targets with committed corpora |
| `cargo xtask gen-fixtures` | regenerate `tests/fixtures` with pinned C git; verify committed fixtures unchanged |

## 9. CI design (GitHub Actions)

One workflow, four jobs (macOS + Linux matrix where cheap):

1. **unit** — `cargo xtask test` + coverage gate.
2. **differential** — build C git from this tree, `cargo xtask differential`.
3. **scoreboard** — `cargo xtask scoreboard`; fails on regression.
4. **fuzz** — `cargo xtask fuzz` short budget.

All jobs gate on every commit to `master` and on PRs.

## 10. Fixture policy

- Every on-disk format has a committed golden fixture produced by the pinned
  C git.
- Every fixture is consumed by both the unit and differential suites.
- Fixtures are reproducible: `cargo xtask gen-fixtures` regenerates and verifies
  the `.checksums` file; CI rejects uncommitted fixture drift.

## 11. "No manual intervention" rule

- Every gate above is one command.
- `scoreboard.json` makes "the t/ suite passes" machine-checkable.
- CI is the single source of truth for phase completion.
